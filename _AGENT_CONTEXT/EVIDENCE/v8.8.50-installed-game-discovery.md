## Reproduction / root cause
The universal registry already contains Steam, Epic and GOG discovery, but the normal startup path special-cases Monster Hunter: World and the Games view initially only loads `games.json`. General installed-game discovery runs only when the user finds and presses **Find Installed Games**. A machine with MHW therefore commonly opens with a registry/UI containing only MHW even when other supported-store games are installed.

A second coverage weakness is Steam executable resolution: manifests identify install roots but not the executable, while the current fallback searches only a few fixed directories. Games with a legitimate executable nested elsewhere under the install root are skipped.

## Intended correction
1. Make the Games view perform one idempotent best-effort installed-game discovery on its first refresh, while retaining the manual rescan action.
2. Keep discovery bounded to launcher/install metadata; do not recursively crawl whole drives for arbitrary executables.
3. Refactor candidate registration behind a deterministic seam and add regression coverage that proves a first Games refresh can register multiple non-MHW/MHW candidates.
4. Strengthen bounded executable lookup within a discovered game root and add Xbox Games top-level install discovery without widening to unrelated software.
5. Isolate source-specific discovery failures so one inaccessible launcher does not suppress the others.
6. Record the defect precedent, visible patch metadata, verification and successor handoff before completion.

## Candidate implementation checkpoint
Implemented on the task branch:
- `GameProfileRegistry` now composes Steam, Epic, GOG, and Xbox discovery with per-source failure isolation; launcher probing occurs outside the short registry mutation lock, while registration/manual mutations serialize.
- Steam discovery reads both user/machine install roots, all configured `libraryfolders.vdf` libraries, and every local app manifest.
- Known launcher candidates preserve their proven install root when generic profiles are created.
- Executable fallback is a bounded breadth-first search inside that proven root only: depth 4, at most 384 directories, reparse points skipped, support/redistributable trees skipped, strong title matches short-circuit early, and known crash-handler/installer/anti-cheat helpers are filtered without blanket-rejecting legitimate `Crash*` game executables.
- Xbox discovery reads direct `XboxGames/<title>/Content` installs on ready fixed drives; it never scans unrelated drive trees.
- `GamesPageViewModel.Refresh()` loads the existing registry immediately, then schedules one background discovery pass per view-model lifetime; newly found rows are marshalled back to the WPF dispatcher, so ordinary startup no longer blocks on launcher scanning or requires the user to find the manual rescan action.
- Manual **Find Installed Games** remains a full rescan and **Add Game** remains the fallback for unsupported/portable/custom-launcher titles.
- The manual scan UI now names Xbox alongside Steam/Epic/GOG.
- Integration regressions cover first-refresh MHW + generic registration, one-time discovery, Steam multi-library manifests, nested executable lookup, Xbox Content-root discovery, and helper filtering.
- `BUG_PRECEDENTS.md` and LR-060 capture the prevention invariant.

No whole-drive executable crawl, uninstall-registry software guessing, catalog-provider behavior, deployment semantics, or game-adapter conflict semantics were added or widened.
