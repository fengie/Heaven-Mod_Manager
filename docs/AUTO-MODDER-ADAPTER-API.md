# Auto Modder adapter API and patch-plan IR v1

Status: foundation contract implemented in MhwModManager.Core.

## Trust boundary

Recipes are declarative data. Adapters are executable trusted code and therefore sit behind an explicit registry.

An adapter exposes a stable ID, implementation version, and the exact AutoModOperationKind values it supports. A recipe declares an adapter ID plus a bounded version range. Planning fails when the adapter is missing, outside the declared range, or does not advertise the requested operation.

The first registry intentionally does not auto-load executable code from mod archives or recipe packs.

## Version ranges

The implemented foundation supports exact dotted versions and whitespace-separated comparisons such as:

    1.2.0
    >=1.0.0 <2.0.0
    >=1.3.0 <=1.9.5

Prerelease/build metadata negotiation is not part of this first contract.

## Patch-plan IR

AutoModPatchPlan is deterministic for the same normalized recipe, normalized inputs, and adapter registry.

Each AutoModPatchOperation records:

- zero-based sequence;
- recipe step ID;
- adapter ID;
- typed operation kind;
- source alias;
- resolved target;
- resolved field;
- resolved old-value assertion;
- resolved new value.

The planner does not mutate source bytes. It only validates and lowers declarative recipe steps into the typed IR.

## Adapter execution API direction

The executable adapter layer that applies a patch plan must preserve the following v1 contract:

1. Identify whether the adapter can read the declared source format.
2. Parse source bytes into a typed internal model without modifying source bytes.
3. Validate the parsed model.
4. Apply only typed operations advertised by SupportedOperations.
5. Serialize deterministically.
6. Reparse and validate generated bytes.
7. Produce semantic before/after diff entries.
8. Enforce record/depth/size budgets and cancellation.

The current foundation deliberately stops at registry/capability negotiation and deterministic patch planning. Real parser/serializer adapters are the M2 vertical-slice boundary.

## Patch safety

Unknown operation semantics fail closed. An adapter may not reinterpret an unsupported operation, use recipe data as executable code, or turn a recipe path into unrestricted filesystem access.

Adapters receive source/output material through manager-owned boundaries. Live-game mutation remains owned by the existing deployment transaction.
